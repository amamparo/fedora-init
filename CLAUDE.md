# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Keep documentation in sync

When a change alters behavior, commands, role conventions, keybindings, or gotchas, update the documentation in the same change — this file, README.md, and any task-file header comments that describe the affected behavior. README.md is the user-facing doc (what the roles do and how to run them); CLAUDE.md is the contributor-facing doc (architecture, conventions, gotchas). A PR that changes what a role does but not the docs is incomplete.

## Commit and push at good stopping points

Whenever the work reaches a coherent, self-contained stopping point — a role added, a gotcha fixed, docs synced — commit and push without waiting to be asked. A "good stopping point" means the tree is consistent: docs match behavior (see above), `ansible-playbook site.yml --syntax-check` passes, and the change stands on its own. This repo does NOT use PRs or feature branches: commit straight to `main` with a descriptive message and `git push origin main`. Do NOT run the playbook to "verify" before committing — the safe checks in the section below are the gate.

## What this is

An Ansible playbook that configures a fresh Fedora Workstation (GNOME) install, targeting Fedora 44 / GNOME 50. The only entry point is:

```sh
./install.sh                # bootstrap the toolchain + run every role
./install.sh battery zsh    # run roles whose tag contains a substring
./install.sh --check        # dry run (any dash-arg passes through to ansible-playbook)
curl -fsSL https://raw.githubusercontent.com/amamparo/fedora-init/main/install.sh | bash   # no checkout
```

**Running the playbook mutates the host** (installs/removes dnf packages, masks systemd units, changes the login shell). Don't execute it to "test" a change unless the user asks — even `--check` prompts for sudo. The safe checks are:

```sh
ansible-playbook site.yml --syntax-check
ansible-lint --offline        # policy in .ansible-lint; passes the production profile
bash -n install.sh
python3 -m py_compile library/*.py
```

## Architecture

- `install.sh` — orchestrator and bootstrapper. If it can't find `site.yml` next to itself (piped from curl, or a stray lone copy), it downloads the GitHub tarball to a temp dir and re-runs from that copy. Otherwise it: reattaches stdin to `/dev/tty` (under curl|bash stdin is the exhausted pipe; the sudo prompt and the keyring pause both need the terminal), authenticates sudo **once, interactively** (`sudo -v` — password or fingerprint), installs a one-line sudoers drop-in (`/etc/sudoers.d/fedora-init`: `Defaults timestamp_type=global`, visudo-checked before install, guarded by content compare; the first install flips the record type, so that run authenticates a second time to write a global record), starts the `sudo -n -v` keepalive loop, installs the toolchain guarded by `rpm -q` (ansible-core, the community.general and ansible.posix collection rpms, python3-libdnf5, python3-psutil, rsync — all stock Fedora packages), maps bare arguments onto tags by substring against `roles/*` dir names, bootstraps the Bitwarden secrets session when due (see the aws gotcha; skipped when the seed target exists, under `--check`/`-C`, or when the tag selection excludes aws; a failed sign-in warns and continues rather than aborting the run; the shared EXIT trap `bw lock`s the session even when the play aborts and sweeps the bw download tempdir), and runs `ansible-playbook site.yml --diff` with **no become password at all**: every per-task sudo authenticates via the global timestamp record, skipping PAM entirely. This design is forced, not chosen: on fingerprint-enrolled Fedora, pam_fprintd runs before pam_unix in sudo's PAM stack and — probe-verified in ansible's exact become context (pty stdin, piped stdio) — blocks silently in the fingerprint wait without ever emitting a password prompt, so become-with-password times out no matter how the password is delivered; and sudo's default tty-scoped timestamps can never match become's fresh throwaway ptys, which is why the drop-in scopes the record to the user (trade-off: while a record is live, any same-user process can sudo without re-auth — acceptable on this single-user machine, documented in README, reverted by deleting the drop-in).
- `site.yml` — one play: `hosts: localhost`, local connection, `gather_facts: false`, **`become: false` at play level**, `force_handlers: true` (a handler notification lost to a mid-play abort is never re-fired by a converged re-run). A `package_facts` pre-task (tagged `always`, `check_mode: false`) is the rpm -q guard layer. Roles run in the old NN-module order; each is tagged with its role name, underscores as hyphens.
- `roles/<name>/` — one concern per role: `tasks/main.yml`, optional `handlers/main.yml`, assets in `files/`. `roles/common/tasks/gnome_extension.yml` is a shared include (parameters: `ext_uuid`, `ext_role`, `ext_has_schemas`) used by window_snapping and no_overview.
- `library/` — two custom check-mode-aware modules for the D-Bus mutations nothing stock covers: `mutter_display_config.py` (DisplayConfig `ApplyMonitorsConfig`) and `login_keyring.py` (gnome-keyring `ChangeWithMasterPassword`). Both must run as the desktop user on the session bus, never under become.
- `ansible.cfg` / `hosts.ini` — local inventory, `gathering = explicit`, in-repo `roles_path`/`library`.

## Conventions (enforced by review, not tooling)

- **One concern per role — and an add-on belongs to its host's role.** Something that only exists to extend another thing this repo installs goes in that thing's role, not its own: the caveman plugin lives in claude_code, podman-tui/podman-docker live in podman. The test is dependency direction: if the candidate is meaningless without the host, merge it. Do NOT merge siblings that merely share machinery (window_snapping and no_overview both use the gnome_extension include but are separate concerns) or incidental coupling (mise's shell hook rides the zsh role's zshrc asset, but a runtime manager isn't shell config). When merging costs a tag, the substring matcher usually still covers it (`./install.sh claude` reaches the caveman tasks).
- **become is opt-in per task**, only for system mutations (dnf, /etc, systemd, usermod). Anything touching the user session — dconf writes, session D-Bus, `$HOME` files, user-level installers — must NOT have become: run as root it would configure root's desktop, the classic failure the old bash modules guarded with "no sudo here" comments. Never set become at play level.
- **Zero-network converged re-run** is a hard requirement — with exactly two deliberate exceptions: the updates role (drift from upstream is undetectable offline) and podman's always-latest install (aaron's call; see both gotchas). The dnf5 module refreshes repo metadata even for no-op transactions, so every package task guards on `ansible_facts.packages` (exact rpm names — virtual provides can't false-match). Same discipline for anything else that would touch the network when nothing changed (the oh-my-zsh clone gates on its payload file; the tarball/curl installers gate on presence probes).
- **Check-mode honesty**: `./install.sh --check` on a converged machine must print every task ok/skipped with zero diffs — and on a *fresh* machine it must not crash. Read-only probes that later conditionals depend on get `changed_when: false` + `check_mode: false` (so they still run under --check). Mutating commands get an explicit `changed_when`. Registered results of tasks *skipped* in check mode lack attributes — guard downstream dereferences (`foo.path is defined`), the pattern the tempfile-using roles follow. Two fresh-`--check` gates recur: dnf5 resolves package specs even in check mode, so an install whose repo file was only *simulated* needs `not (ansible_check_mode and <repo_copy> is changed)` (brave, vscode) or `not ansible_check_mode or <release rpm> in ansible_facts.packages` (multimedia); and systemd_service fails on units whose package install was only simulated (battery).
- `gather_facts` is false: `ansible_env` does not exist. Use `{{ lookup('env', 'HOME') }}` (controller == target under the local connection).
- dconf values are **GVariant text**: strings `"'prefer-dark'"`, booleans `"true"`, doubles `"0.19"`, empty string arrays `"@as []"` (a bare `[]` is untyped and invalid), non-empty `"['a', 'b']"`. When a value comes from a YAML list var, render it explicitly (`| string`) — a bare single-variable template resolves to a native list, not text.
- Comment density is a feature: the task files carry the WHY comments the bash modules had. Keep lint clean (`.ansible-lint` skips exactly two style rules, with reasons in that file); prefer a `# noqa: rule` with justification over weakening a task.

## The GNOME extensions

`roles/window_snapping/files/rectangle@amamparo/` and `roles/no_overview/files/no-overview@amamparo/` are bundled, self-authored GNOME Shell extensions (ESM, GNOME 48–51), not vendored third-party ones — edit them directly here. The shared `gnome_extension.yml` mirrors them into `~/.local/share/gnome-shell/extensions/` with rsync; its rsync_opts are load-bearing for convergence (`--exclude=gschemas.compiled` — exists only in the installed copy; `--checksum` — tarball and git-checkout mtimes differ for identical content; `--omit-dir-times` — glib-compile-schemas rewrites schemas/ and bumps the dir mtime, which would re-report changed and re-compile forever). Schemas compile only when the sync changed (rectangle only). Enablement **merges additively** into `/org/gnome/shell/enabled-extensions`: the effective list is probed via `gsettings get` (NOT `dconf read` — vendor defaults like Fedora's background-logo live in gschema overrides, invisible in the user db) and the repo's `gnome_extensions_enabled` (site.yml) is unioned in — never overwritten, matching the old `gnome-extensions enable` append semantics; the "shell hasn't rescanned" race is gone because the write path IS the old fallback.

For rectangle: keybindings are declared in `schemas/*.gschema.xml` (the `as`-typed keys), consumed by name in `extension.js` (`KEYS`); `_unmaximize()` carries a GNOME ≤48 vs ≥49 API fallback. `metadata.json`'s `shell-version` gates which GNOME versions load an extension, and Wayland can't hot-reload GNOME Shell — extension changes take effect at logout/login.

## Gotchas encoded in the roles

- updates: sanctioned exception to the offline-converged-re-run rule, and it runs FIRST — later roles then resolve against fresh metadata. Its very first task writes `max_parallel_downloads=8` into `/etc/dnf/dnf.conf` (`community.general.ini_file`, become): the ONLY safe parallelism in this single-host play. libdnf5 downloads 3 packages at a time by default; every dnf transaction in the repo inherits the bump, so download phases overlap while the serial rpm transactions (one lock) never do — order untouched, check-mode honest, idempotent. Cross-TASK concurrency was rejected on evidence: async `poll: 0` is the only intra-host mechanism and it STARTS the real background job even under `--check` (verified: `started=True` in a dry run), which would execute installs during `./install.sh --check` — a hard violation of check-mode honesty. `forks` does nothing with one host; `pipelining` is ssh-only (local connection here). 8 is the Fedora-mirror sweet spot (past ~10, mirrors throttle). `update_cache: true` is what actually delivers the fresh-metadata promise: `state: latest` alone trusts any cache inside libdnf5's expiry window, and hours-stale metadata referencing mirror-pruned rpms 404'd podman-tui twice before this was understood. `state: latest` on `*` carries a `package-latest` noqa — latest is the concern here and in podman, nowhere else. fwupd exit codes (verified live): `get-updates` rc 0 = updates available, rc 2 = nothing to do — hence `failed_when: rc not in [0, 2]`; `update --assume-yes --no-reboot-check` applies without prompting, and staged firmware takes effect at reboot (the role says so). fwupd/flatpak tasks are guarded on the packages existing — Workstation ships both, minimal installs may not.
- snapshots: snapper + libdnf5-plugin-actions + btrfs-assistant (all stock rpms) — pre/post btrfs snapshots of / around every dnf5 transaction, ordered right after updates so the rest of the very first run is already covered. `files/snapper.actions` is upstream dnf5's canonical DNF4-snapper-emulation example with two deliberate deltas, both explained in its header: `-c number` on both `snapper create` calls (number-cleanup only prunes snapshots carrying the "number" cleanup algorithm — upstream's example accumulates forever) and an inline python3 rpmdb WAL checkpoint before the post snapshot (rpm's sqlite runs WAL mode; a snapshot with unflushed frames makes rpm report packages that `snapper undochange` already reverted — SysGuides' F44 finding; python3 stdlib, no sqlite3 CLI dependency). Actions format: FIVE colon-separated fields, backslash-escaped spaces stay one argv element, `${...}` substitutes before unescaping, and there is NO shell unless the command is `sh -c` — the python line's quotes are python syntax, not shell. Plugin errors never abort the transaction (raise_error defaults to 0). Config creation is `create-config` guarded by `creates:` on /etc/snapper/configs/root; retention limits are SEEDED one-time on creation (`set-config` rewrites the file — converged management would fight snapper, the reaper.ini class), followed by a one-time `restorecon -RF /.snapshots` (the fresh subvolume is unlabeled). Timers ship disabled per Fedora's spec; enablement carries the battery fresh-`--check` gate. Scope: /home is a separate subvolume, so root snapshots never cover user files (same-disk undo only — offsite backup is deliberately out of scope here); /var IS inside root, so rollbacks rewind logs and system-side container state. Post-rollback trap documented in the role, not automated: dnf failing with "cannot copy: packages.toml" wants `mkdir -p /usr/lib/sysimage/libdnf5` + restorecon. Substring: `./install.sh snap` matches BOTH window-snapping and snapshots.
- hostname: sets the static hostname to `thinkpad` (LAN-reachable as `thinkpad.local`) via `ansible.builtin.hostname` with an explicit `use: systemd` — there is NO `FedoraHostname` class (verified: 35 distro subclasses, zero mention of Fedora), so autodetection rides one `is_systemd_managed()` canary whose fallback is base `Hostname` → `UnimplementedStrategy`, a HARD FAIL rather than a degrade; naming the strategy skips that path. `become: true` because `SetStaticHostname` is the polkit action `org.freedesktop.hostname1.set-static-hostname` (auth_admin_keep), which root short-circuits — no agent, no prompt under this repo's passwordless become. **The handler MUST be `state: restarted`, never `reloaded`:** avahi consults `gethostname()` exactly ONCE, in `avahi_server_new()`, and watches nothing afterwards (inotify covers only /etc/avahi and /etc/avahi/services; no `org.freedesktop.hostname1` subscription — `strings /usr/bin/avahi-daemon | grep hostname1` is empty; netlink is RTMGRP_LINK/IFADDR, interfaces not names), while `reload_config()` — reached by SIGHUP, `avahi-daemon -r`, and therefore the unit's own `ExecReload=` — reloads static services/hosts/resolv.conf/browse domains and NOT the host name, so a reload leaves the machine answering as the old name until reboot. The daemon's "-2" conflict rename is not a counterexample (it derives from the in-memory name in response to a packet). Equally, never write `/etc/hostname` with `copy`: it bypasses hostnamed, the running kernel name stays stale, and since avahi publishes whatever `gethostname()` returns the restart would then re-read the OLD name — the module sets permanent-then-transient (only `SystemdStrategy` overrides the base class's reverse order, "to avoid NetworkManager complaints"). **NEVER verify a rename with `getent`/`resolvectl` on this machine** — resolved answers the machine's own `<hostname>.local` locally without consulting avahi (mDNS is `-mDNS` in resolved on Fedora; avahi owns 5353): resolved says so itself, `resolvectl query fedora.local` closing with `Data from: synthetic` and returning every local address including ones avahi is not publishing, while a foreign `.local` name fails outright. Use `avahi-resolve -n <name>.local`, another host, or `busctl call org.freedesktop.Avahi / org.freedesktop.Avahi.Server GetHostName` (which also catches a silent `-2`). **avahi/nss-mdns are ASSUMED, never installed** (the updates-role fwupd/flatpak guard-on-presence precedent): Workstation ships both, and `nss-mdns`'s posttrans scriptlet runs `authselect enable-feature with-mdns4` — installing it would drag this repo into authselect, whose `with-fingerprint` the whole become design rests on. The guard is a PLAIN `'avahi' in ansible_facts.packages`, deliberately NOT the tailscale/battery `not ansible_check_mode or …` form: this role installs nothing, so an absent avahi is genuinely absent rather than simulated, and the tailscale form would evaluate true on a real run and hard-fail systemd_service on a unit that will never exist. Do NOT touch `/etc/hosts` (`files` precedes `myhostname` in the nsswitch hosts line, so a `127.0.0.1 thinkpad` entry would SHADOW the real LAN address; "fedora" is in no hosts file today and resolves fine both ways — the `sudo: unable to resolve host` folklore predates nss-myhostname), do NOT swap `mdns4_minimal` for dual-stack `mdns_minimal` (nss-mdns's README: IPv6-first apps time out), do NOT add a firewalld task (default AND active zone is FedoraWorkstation, which already permits 1025-65535/udp, so 5353 is open — the `mdns` service entry would fork a vendor zone file into a frozen copy for nothing), do NOT enable `publish-workstation` (pristine `config(noreplace)`; `_workstation._tcp` is the administrative "browse for all PCs on the LAN" advert in `avahi-daemon.conf(5)`'s own words, consumed by avahi-browse/avahi-discover and NOT by file managers, orthogonal to the `.local` A record, and avahi names it `<hostname> [<mac address>]` — a MAC broadcast on every roamed network). Today's "fedora" is `DEFAULT_HOSTNAME` in `/usr/lib/os-release` (fedora-release-identity-workstation), NOT DHCP and NOT `/etc/hostname` — which exists holding one newline as `%ghost %config(noreplace)` from systemd; `hostnamectl --json=short` reports HostnameSource `default`, StaticHostname null. A valid static name is also NetworkManager's own documented opt-out from touching the hostname, so no `hostname-mode=none`. The module's `--pretty --static` call really does set the pretty name (hostnamectl drops a redundant one only on its no-flags path), CREATING `/etc/machine-info` and moving GNOME's "Device Name" and the Bluetooth adapter alias — SEEDED once, never converged, since change detection reads only `--static`. Ordered slot 3, after snapshots (inside the first run's rollback coverage) and BEFORE tailscale, so the first-ever `tailscale up` registers `thinkpad`; never `tailscale set --hostname`, which permanently un-sticks the tailnet name from the OS hostname. Substring: `./install.sh host` matches BOTH hostname and ghostty; `hostname`/`name` hit only this role.
- steam: from RPM Fusion nonfree, so it MUST stay ordered after multimedia (which installs the release rpms); carries the same fresh-`--check` gate on `rpmfusion-nonfree-release`.
- battery: `tlp` declares `Conflicts: tuned` (`tuned-ppd` merely depends on tuned). The stock stack is removed *before* installing so its orphaned deps get swept — but the dnf5 *module*, unlike the CLI, only sweeps with `autoremove: true` (it wires `clean_requirements_on_remove` to that flag, default off); the removals here and in brave set it. Removals are guarded per exact rpm name because `tlp-pd` *provides* `power-profiles-daemon`. Unlike the dnf5 CLI, the module no-ops when removing an absent package — the guards still matter for the offline re-run. `ansible.builtin.systemd_service` fails on units whose file doesn't exist (LoadState probe, even under --check), so power-profiles-daemon.service — whose unit vanished with the package — is masked via plain `systemctl mask` guarded by `creates:` on the mask symlink; the systemd-rfkill units ship with systemd itself and use the module, but enable/start of tlp.service+tlp-pd.service is gated `not ansible_check_mode or <rpm> in ansible_facts.packages` — on a fresh --check the install was only simulated and the module would hard-fail on the missing units. TLP's docs require masking systemd-rfkill. `tlp start` is a handler (fires only on change, where the bash module ran it every time; `force_handlers` keeps a notification from being lost to a later role's failure). powertop is measurement-only — no autotune service, it would fight TLP over the same sysfs knobs.
- window_snapping / no_overview: extension install + enablement is the shared `gnome_extension.yml` (see above). GNOME's stock bindings collide with all four tiling keys (`shift-overview-up/down` defaults to Super+Alt+Up/Down; `switch-to-workspace-left/right` includes Super+Alt+Left/Right) and Mutter resolves duplicates nondeterministically — the role clears the overview pair and rebinds workspace switching to Super+Alt+PageUp/PageDown. Check both `org.gnome.shell.keybindings` and `org.gnome.desktop.wm.keybindings` schemas before adding any new binding. Super+Alt+F is GNOME's native `toggle-maximized`, bound *alongside* its stock Alt+F10 (a bare set would silently drop it); `toggle-fullscreen` is reset (dconf `state: absent`) because an earlier revision bound it to the same key. For no_overview: opening the overview at login is hardcoded in gnome-shell (upstream gnome-shell!4009 unmerged as of GNOME 50); since GNOME 50 extensions initialize after the startup animation begins, so a brief flash is unavoidable. Don't add a second hide-overview mechanism alongside it — running two is a reported crash source.
- cli_tools: one guarded dnf5 transaction for the modern-CLI baseline (fzf ripgrep fd-find bat jq yq btop eza zoxide uv — all stock Fedora rpms; the battery difference-filter guard). Name traps, verified against the F44 package index: the rpm is `fd-find` but the binary is plain `fd` (Debian's fdfind rename doesn't apply), and Fedora's `yq` IS mikefarah's Go yq v4 (no go-yq rpm exists) — don't "correct" either. One role deliberately: a baseline toolkit is one concern; eight one-package roles would be noise. Shell wiring lives in roles/zsh/files/zshrc, NOT here (the mise rule — a lineinfile would diverge from the zsh role's cmp-copied asset): fzf's bindings are installed-but-disabled by the rpm (`source /usr/share/fzf/shell/key-bindings.zsh`; its completion auto-loads from zsh site-functions — never source that half manually), zoxide ships no profile.d hook (the `eval "$(zoxide init zsh)"` is mandatory). uv complements mise, never replaces it: mise pins runtimes, uv does packaging/`uvx` (how many MCP-server configs launch stdio servers). Substring: `./install.sh cli` also sweeps github-cli; `tools` is the unique handle.
- zsh: oh-my-zsh via the git module, but gated on the payload file `oh-my-zsh.sh` (a dir without it is a broken half-install — moved aside to `~/.oh-my-zsh.broken` and recloned), NOT left to the git module's own idempotency: for an existing clone the module fetches origin every run, which would break the offline re-run and silently become an updater. The one-time `~/.zshrc.pre-fedora-init` backup (README references the name) is a cmp probe + guarded copy, not `backup: true` (which timestamps).
- git_workspace: the ssh key is presence-guarded via `creates:` — NEVER regenerate an existing key (it may be enrolled with GitHub; silent replacement breaks every remote). No passphrase, deliberately (the login-keyring LUKS trade-off). The pubkey debug is gated `not ansible_check_mode` — under fresh --check the file doesn't exist to read. Nautilus bookmarks live in `~/.config/gtk-3.0/bookmarks` even for GTK4 Nautilus ("URI [label]" lines, picked up live); the bookmark is grep-probed by URI and only *added* when absent — a lineinfile regexp rewrite would reset a user-renamed label, the Toolbox-autostart trap again. **SSH commit signing** rides here too: git's SSH backend signs commits+tags with the SAME ed25519 key (no separate GPG key), set via `community.general.git_config` `scope: global` — plus the global `user.name`/`user.email` a fresh gitconfig lacks (signing needs an author identity). All `~/.gitconfig`/`$HOME` writes, NO become (root's gitconfig otherwise — the dconf-as-root class). The `allowed_signers` file (local `git verify-commit`) is guarded on a `stat` of the pubkey (`check_mode: false`, so truthful under --check) — `lookup('file', …pub)` in its `content` would crash a fresh --check where the key was only simulated, the same trap the pubkey debug dodges. GitHub "Verified" needs the key re-added as a *Signing* key (separate slot, same key) — not automatable, so it's not attempted. **delta** rides here too (add-on rule — a git pager is meaningless without git): the `git-delta` rpm plus core.pager/interactive.diffFilter/delta.navigate/merge.conflictStyle=zdiff3 through the same git_config pattern — repo-declared converged values (the aws region/output class: edit the task, not `git config`), user scope, NO become. The pager engages only on a tty, so scripts and Claude Code see plain git output; delta.side-by-side stays unset deliberately (too wide for the laptop panel).
- github_cli: `gh` from stock Fedora repos (`updates`) — plain dnf5 + package-facts guard, NO vendor `.repo` and so NO fresh-`--check` repo gate (contrast vscode/tailscale). Separate role, not folded into git_workspace: gh authenticates via its own token/HTTPS flow independent of the ssh key, so the add-on merge test fails (like window_snapping vs no_overview). `gh auth login` is a browser/device flow, not automatable — surfaced as a debug nudge (gated `is changed and not ansible_check_mode`), the tailscale-`up` pattern. Substring quirk: `./install.sh gh` also matches ghostty (tag "ghostty" contains "gh"); `./install.sh github` hits only this role.
- aws: awscli2 is a stock Fedora rpm (plain dnf5 + package-facts guard, the github_cli pattern). The access keys come from **Bitwarden** at seed time, never from the repo — and the sign-in lives in install.sh, NOT a task: the `community.general.bitwarden` lookup shells out to `bw` on the CONTROLLER, and bw's interactive prompts (email + master password + TOTP; the cloud can additionally demand the personal API-key client_secret, its bot check) need the tty tasks don't have. install.sh installs `bw` presence-guarded into `~/.local/bin` (single Node-bundled static binary — no rpm exists, no self-update, the jetbrains presence-is-terminal class; unzipped with `python3 -m zipfile`, dodging an unzip rpm) and exports `BW_SESSION`, gated three ways against needless prompts: seed target (`~/.aws/credentials`) absent + not `--check`/`-C` + tag selection reaches aws (the passthru `--tags` form is approximated by a word-scan, so `--skip-tags aws` is an accepted false positive — a needless prompt, nothing worse, since sign-in failure is non-fatal: install.sh warns and runs the play sessionless). `BW_SESSION` is inherited by every child the play spawns while it lives — the same single-user trade-off class as the sudo global timestamp, bounded by the EXIT trap's `bw lock` (which fires even on an aborted play — a success-only lock would strand a valid session exactly when a failed run leaves one). The role's fetch (set_fact) and seed (copy) BOTH carry `no_log` — install.sh always passes `--diff` and the rendered credentials file IS the secret — and gate on the same triple (probe absent, `BW_SESSION` non-empty, `not ansible_check_mode`; a session-less unconverged run prints a nudge instead of skipping silently). The lookup is exact-name (the plugin equality-filters bw's fuzzy `--search`) with `result_count=1` — a missing or ambiguous `aws` item fails loudly, never seeds an arbitrary match. Item shape: login item named `aws`, username = Access Key ID, password = Secret Access Key. `~/.aws/credentials` is SEEDED ONLY WHEN ABSENT — after that rotation via `aws configure` must win (the bookmark rule), and the absence gate doubles as the zero-network + zero-prompt convergence guard; region/output in `~/.aws/config` are repo-declared preferences managed converged via ini_file (the dconf class). All `$HOME` writes NO become. CLI 2FA limits: TOTP/email/YubiKey-OTP only — an account locked to passkey/FIDO2-only can't sign in from the CLI, so keep TOTP enrolled.
- appindicator: GNOME dropped legacy tray icons in 3.26; apps that still publish one (claude_desktop's TrayIconLinux.png, the tailscale applet) show nothing without this. Renaming rLive's zip to match its internal theme name, the Theme Adjuster, the ModPack and LBX Stripper were all tried or ruled out — none can fix a layout engine that never runs; rLive's screenshots are REAPER-6-era. **MyDaw** (sineforge) is the only thing that really delivers Ableton-in-REAPER and it is Windows/macOS only, no `.so`. **Diagnostic trap that cost hours:** two themes can be told apart ONLY by their WALTER layout, not by colour sampling — a "good" render was mistaken for rLive for a long time when it was actually still Reapertips, because `lastthemefn5` pointed at rLive while REAPER had silently fallen back. Always verify a theme swap by cropping the TCP and diffing against a known baseline, never by eyeballing the palette. **Launching REAPER from a non-GUI shell breaks it silently:** SWELL calls the X11-specific `gdk_x11_*` API, so with `GDK_BACKEND=wayland` in the environment GDK opens a Wayland display, every `gdk_*` call gets NULL, and REAPER starts **windowless** while still holding its single-instance lock — which then swallows the user's own launcher clicks. gnome-shell sets no `GDK_BACKEND`, so GUI launches are fine; only tooling shells are affected (`env -u GDK_BACKEND` to test). **Nuking ~/.config/REAPER destroys `reaper-license.rk`** (the purchased licence) and the ALSA device config — back the directory up before any such experiment. The Ableton work that SURVIVES is the navigation half, which is theme-independent. **Reapertips' own "Perfect Setup" guide is VENDORED at `docs/reapertips-perfect-setup.pdf`** (80pp, ~19 MB, same author as the theme; `docs/` exists for exactly this — provenance that is not an installed asset, so it does NOT go in `roles/reaper/files/`, where everything else gets copied to the machine). It is the source for most of `templates/reaper.ini.j2`, and the page numbers in the role's manual-steps debug refer to it. **The verification rule is what decides what gets encoded:** mespotine's config-var reference (`Docs/Reaper-ConfigVariables-Documentation.txt` in github.com/mespotine/ultraschall-and-reaper-docs — download and grep it, don't fetch the HTML mirror, which 404s) is **REAPER 5.95-era**, so every REAPER-7-only tip in the guide — the item selection indicator (p21), folder-collapse modes (p32), visual track spacer size (p35), render block size (p60), auto record-arm on select (p51) — has NO documented variable and goes in the nudge with its page number rather than being reverse-engineered. Same for `projtakelane` (p49): it IS in the reference but its entry lacks the boilerplate "Stored in reaper.ini under the same name in the section REAPER", and that sentence's presence/absence is the actual test for whether a key belongs in the template. Encoded keys and their arithmetic: `splitautoxfade=40` (p39; `&8` is INVERTED — 1 turns the auto-fade checkbox OFF — and `&32` is REAPER-7-era and undocumented, so 40 is taken WHOLE from a live 7.78 with the guide applied rather than reconstructed), `hwfadex=1` (p40; `&1` fade-out-on-stop kept, `&2` fade-in-on-start cleared), `itemicons=823807` (p41; 511 for the nine button bits + 4096 for both Item Properties boxes off + 32768 for REAPER's own fade-handle default + 262144 + 524288), `recaddatloop=23044` (p50; `&4` discard incomplete, and the threshold percentage is a plain 7-bit number one byte up, so 90*256+4), `midieditor=33` (p65/p68; `&1` one-editor-per-project, `&32` close-on-delete unchecked), `loopnewitems=0` (p42), `projgridmin=18` (p26). **Bitfields are spelled out bit by bit in the template because writing one key sets ALL of its bits** — a value pasted without the arithmetic silently changes preferences the guide never mentioned, which is why `itemicons` declares REAPER's fade-handle default explicitly instead of pretending it isn't being set. **The seed alone reaches nobody who has already run REAPER**, so the keys worth having are ALSO listed in `reaper_ini_keys` (a `vars:` on the probe task in tasks/main.yml) and back-filled with `lineinfile` + `insertafter: ^\[REAPER\]` — probed ONE KEY AT A TIME (a joint probe skips the whole set the moment any one member exists) and added only where absent, so REAPER's rewrite-at-exit and any in-app change always win. Template and `reaper_ini_keys` must be kept in sync; the template header says so. **Two deliberate conflicts between the guide and Ableton parity, both resolved on the record:** `loopnewitems` was REVERSED from 1 to 0 (the guide's p42 extend-don't-loop beat the "a Live clip loops when you drag its edge" reasoning — and aaron's own machine had already landed on 0, which settled it), while `zoommode` stays 0 and does NOT take the guide's p25 mouse-anchored horizontal zoom (Live anchors on the selection; `vzoommode=3` already matches the guide because Live's Option+scroll IS pointer-anchored). **What stays manual and why**, beyond the undocumented keys: mouse-modifier behaviour IDs (p37 multi-fade, p43 limit-item-edges, p62 one-click note insert) are per-context indices REAPER only reveals through its own "Export ReaScript to set these modifiers for this context" button; and the p47 E/Q record shortcuts are NOT seeded even though both action IDs were verified (`1013` Transport: Record, `40668` Transport: Stop (DELETE all recorded media) — note 40668, not 40667) because the plain-letter KEY encoding in mespotine's `Reaper-KEY-Codes_for_reaper-kb_ini.ini` is self-contradictory (`0_101=E` follows lowercase ASCII but `0_81=Q` follows uppercase, and `0_113` is empty), which is the same "not documented well enough to seed blind" bar the Z/X zoom bindings already fail. The nudge fires on any run that actually changed reaper.ini — seed OR back-fill (`reaper_ini_backfill is changed`) — not seed-only, or a configured machine would never see the checklist. **A lot of the guide is already covered elsewhere in the role and must not be re-added:** SWS (p76) and ReaPack (p77) are installed tasks, hand-scroll on middle-drag (p23) is the `MM_CTX_ARRANGE_MMOUSE` seed, wheel scroll/zoom (p24) is the reaper-kb.ini wheel block, and the theme (p30) is the whole first half of this bullet.

The role now carries a `state: absent` task for the override path (machines that ran the old revision still have the file) plus the on-change `update-desktop-database`. **General rule for this repo: never shadow a vendor `.desktop` to patch `StartupWMClass`** — a copied value is a snapshot of something the vendor owns and changes (`Claude` -> `claude-desktop` -> `com.anthropic.Claude` in three releases) parked in the dir that always wins. Diagnose instead: compare the live `xprop WM_CLASS` (X11) / app_id (Wayland) against the entry's `StartupWMClass`, and fix it upstream. The rule is about SNAPSHOTS, not about shadows as such: brave shadows `brave-browser.desktop` to rename the app, and that is sanctioned because the shadow is **regenerated from the vendor file on every run**, so no vendor-owned value is ever frozen — if a shadow is ever unavoidable again, generate it, never vendor it, and never hand-write a value the vendor owns.
