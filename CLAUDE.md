# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Keep documentation in sync

When a change alters behavior, commands, role conventions, keybindings, or gotchas, update the documentation in the same change — this file, README.md, and any task-file header comments that describe the affected behavior. README.md is the user-facing doc (what the roles do and how to run them); CLAUDE.md is the contributor-facing doc (architecture, conventions, gotchas). A PR that changes what a role does but not the docs is incomplete.

## Commit and push at good stopping points

Whenever the work reaches a coherent, self-contained stopping point — a role added, a gotcha fixed, docs synced — commit and push without waiting to be asked. A "good stopping point" means the tree is consistent: docs match behavior (see above), `ansible-playbook site.yml --syntax-check` passes, and the change stands on its own. This repo does NOT use PRs or feature branches: commit straight to `main` with a descriptive message and `git push origin main`. Do NOT run the playbook to "verify" before committing — the safe checks in the section below are the gate.

## What this is

An Ansible playbook that configures a fresh Fedora Workstation (GNOME) install, targeting Fedora 44 / GNOME 50. The only entry point is:

```sh
./install.sh                # bootstrap the toolchain + run every role
./install.sh battery zsh    # run roles whose tag contains a substring
./install.sh --check        # dry run (any dash-arg passes through to ansible-playbook)
curl -fsSL https://raw.githubusercontent.com/amamparo/fedora-init/main/install.sh | bash   # no checkout
```

**Running the playbook mutates the host** (installs/removes dnf packages, masks systemd units, changes the login shell). Don't execute it to "test" a change unless the user asks — even `--check` prompts for sudo. The safe checks are:

```sh
ansible-playbook site.yml --syntax-check
ansible-lint --offline        # policy in .ansible-lint; passes the production profile
printf '%s\n' install.sh scripts/*.sh | xargs -n1 bash -n   # bash -n parses only its FIRST argument, and a for-loop's status is its LAST iteration's; xargs exits 123 if any file fails
python3 -m py_compile library/*.py
```

`just check` runs exactly that gate (the justfile's other recipes: `install` wraps `./install.sh`, `seed-bitwarden` is the vault upsert — see the aws gotcha).

## Architecture

- `install.sh` — orchestrator and bootstrapper. If it can't find `site.yml` next to itself (piped from curl, or a stray lone copy), it downloads the GitHub tarball to a temp dir and re-runs from that copy. Otherwise it: reattaches stdin to `/dev/tty` (under curl|bash stdin is the exhausted pipe; the sudo prompt and the keyring pause both need the terminal), authenticates sudo **once, interactively** (`sudo -v` — password or fingerprint), installs a one-line sudoers drop-in (`/etc/sudoers.d/fedora-init`: `Defaults timestamp_type=global`, visudo-checked before install, guarded by content compare; the first install flips the record type, so that run authenticates a second time to write a global record), starts the `sudo -n -v` keepalive loop, installs the toolchain guarded by `rpm -q` (ansible-core, the community.general and ansible.posix collection rpms, python3-libdnf5, python3-psutil, rsync — all stock Fedora packages), maps bare arguments onto tags by substring against the role dir names under `roles/<group>/` (it walks `roles/*/*/`, skipping any dir without `tasks/main.yml`, so group names never match — see the `roles/<group>/<name>/` bullet), bootstraps the Bitwarden secrets session when due (see the aws and litellm gotchas; the bw install/sign-in helpers live in `scripts/bw-lib.sh`, sourced by install.sh and by `scripts/seed-bitwarden.sh`; due = some role whose seed target is missing — `~/.aws/credentials` for aws, the `ANTHROPIC_API_KEY=` LINE in `/etc/litellm/litellm.env` for litellm, probed with `sudo -n grep` because the generated master key shares that 0600 file — is reached by the tag selection, never under `--check`/`-C`; a failed sign-in warns and continues rather than aborting the run; the shared EXIT trap `bw lock`s a session this run opened even when the play aborts — a valid BW_SESSION inherited from the shell is borrowed and left alone (`bw_session_opened` in the lib; the function sets BW_SESSION in the caller's shell rather than printing it, because a `$(...)` caller would lose that flag in a subshell); **the sync is part of opening the session**: `bw unlock` only derives the key locally and succeeds on a persisted login whose refresh token has expired, so the first server call — `bw sync` — is what fails, with `invalid_grant` (seen live 2026-09-20), and the lib answers that with `bw logout` + a fresh `bw login`; any other sync failure sets `bw_synced` empty, which install.sh tolerates (a cached vault can still serve the item) and `scripts/seed-bitwarden.sh` treats as fatal (edits need the server) — and sweeps the bw download tempdir), and runs `ansible-playbook site.yml --diff` with **no become password at all**: every per-task sudo authenticates via the global timestamp record, skipping PAM entirely. This design is forced, not chosen: on fingerprint-enrolled Fedora, pam_fprintd runs before pam_unix in sudo's PAM stack and — probe-verified in ansible's exact become context (pty stdin, piped stdio) — blocks silently in the fingerprint wait without ever emitting a password prompt, so become-with-password times out no matter how the password is delivered; and sudo's default tty-scoped timestamps can never match become's fresh throwaway ptys, which is why the drop-in scopes the record to the user (trade-off: while a record is live, any same-user process can sudo without re-auth — acceptable on this single-user machine, documented in README, reverted by deleting the drop-in).
- `site.yml` — one play: `hosts: localhost`, local connection, `gather_facts: false`, **`become: false` at play level**, `force_handlers: true` (a handler notification lost to a mid-play abort is never re-fired by a converged re-run). A `package_facts` pre-task (tagged `always`, `check_mode: false`) is the rpm -q guard layer. Roles run in the old NN-module order; each is tagged with its role name, underscores as hyphens.
- `roles/<group>/<name>/` — one concern per role: `tasks/main.yml`, optional `handlers/main.yml`, assets in `files/`. Roles are grouped by context (2026-09-20): `system` (updates, snapshots, hostname, battery, fingerprint, login_keyring, multimedia, tailscale), `desktop` (window_snapping, no_overview, appindicator, gnome_prefs, ghostty, brave, steam, gimp), `dev` (zsh, cli_tools, git_workspace, github_cli, aws, vscode, podman, mise), `ai` (claude_code, claude_desktop, ollama, litellm, goose, opencode), `audio` (pipewire, qpwgraph, reaper). The group is only a directory to `site.yml`, the tags and the matcher — but ansible finds roles ONLY through `ansible.cfg`'s `roles_path`, a closed list of the five group dirs (plus bare `roles/` for `common`; `roles_path` takes no globs), so a NEW group must be appended there or its roles are found by the matcher and then fail to load; `site.yml` names roles without the group, tags are still the bare role name, and install.sh's matcher walks `roles/*/*/` (skipping anything without `tasks/main.yml`), so `./install.sh <substring>` matches role names only, never group names (`ai` reaches tailscale, not the ai group). Inside a role `role_path` is the grouped dir, and anything that needs a SIBLING role's files must not hard-code `roles/<name>` — the gnome_extension include takes an absolute `ext_src` that callers `set_fact` from their own `role_path` before including, because `vars:` on `include_role` are templated lazily inside `common` (verified: `role_path` there is `roles/common`). Adding a role = pick the group, drop `roles/<group>/<name>/`, add it to `site.yml`. `roles/common/tasks/gnome_extension.yml` is a shared include (parameters: `ext_uuid`, `ext_src`, `ext_has_schemas`) used by window_snapping and no_overview; `roles/common/tasks/ollama_install.yml` (parameter: `ollama_install_tag`), `roles/common/tasks/goose_desktop_install.yml` (`goose_install_tag`) and `roles/common/tasks/litellm_prisma_generate.yml` (no parameter; cmp-gated) are the others, each shared by its role (first install) and updates (upgrade). All go in via `include_role: name: common, tasks_from: …`.
- `justfile` + `scripts/` — `just install [args]` (`./install.sh "$@"`, positional-arguments so quoting survives), `just check` (the safe gate above), `just litellm-master-key` (the admin UI password, `sudo grep` of the env file) and `just seed-bitwarden` (`scripts/seed-bitwarden.sh`, upserts the vault items the roles read; see the aws gotcha). `scripts/bw-lib.sh` is the bw install/sign-in shared with install.sh.
- `library/` — two custom check-mode-aware modules for the D-Bus mutations nothing stock covers: `mutter_display_config.py` (DisplayConfig `ApplyMonitorsConfig`) and `login_keyring.py` (gnome-keyring `ChangeWithMasterPassword`). Both must run as the desktop user on the session bus, never under become.
- `ansible.cfg` / `hosts.ini` — local inventory, `gathering = explicit`, in-repo `roles_path`/`library`.

## Conventions (enforced by review, not tooling)

- **One concern per role — and an add-on belongs to its host's role.** Something that only exists to extend another thing this repo installs goes in that thing's role, not its own: the caveman plugin lives in claude_code, podman-tui/podman-docker live in podman. The test is dependency direction: if the candidate is meaningless without the host, merge it. Do NOT merge siblings that merely share machinery (window_snapping and no_overview both use the gnome_extension include but are separate concerns) or incidental coupling (mise's shell hook rides the zsh role's zshrc asset, but a runtime manager isn't shell config). When merging costs a tag, the substring matcher usually still covers it (`./install.sh claude` reaches the caveman tasks).
- **become is opt-in per task**, only for system mutations (dnf, /etc, systemd, usermod). Anything touching the user session — dconf writes, session D-Bus, `$HOME` files, user-level installers — must NOT have become: run as root it would configure root's desktop, the classic failure the old bash modules guarded with "no sudo here" comments. Never set become at play level.
- **Zero-network converged re-run** is a hard requirement — with exactly two deliberate exceptions: the updates role (drift from upstream is undetectable offline — and that is where the out-of-dnf upgrades for ollama, litellm and opencode live, presence-guarded) and podman's always-latest install (aaron's call; see both gotchas). The dnf5 module refreshes repo metadata even for no-op transactions, so every package task guards on `ansible_facts.packages` (exact rpm names — virtual provides can't false-match). Same discipline for anything else that would touch the network when nothing changed (the oh-my-zsh clone gates on its payload file; the tarball/curl installers gate on presence probes).
- **Check-mode honesty**: `./install.sh --check` on a converged machine must print every task ok/skipped with zero diffs — and on a *fresh* machine it must not crash. Read-only probes that later conditionals depend on get `changed_when: false` + `check_mode: false` (so they still run under --check). Mutating commands get an explicit `changed_when`. Registered results of tasks *skipped* in check mode lack attributes — guard downstream dereferences (`foo.path is defined`), the pattern the tempfile-using roles follow. Two fresh-`--check` gates recur: dnf5 resolves package specs even in check mode, so an install whose repo file was only *simulated* needs `not (ansible_check_mode and <repo_copy> is changed)` (brave, vscode) or `not ansible_check_mode or <release rpm> in ansible_facts.packages` (multimedia); and systemd_service fails on units whose package install was only simulated (battery).
- `gather_facts` is false: `ansible_env` does not exist. Use `{{ lookup('env', 'HOME') }}` (controller == target under the local connection).
- dconf values are **GVariant text**: strings `"'prefer-dark'"`, booleans `"true"`, doubles `"0.19"`, empty string arrays `"@as []"` (a bare `[]` is untyped and invalid), non-empty `"['a', 'b']"`. When a value comes from a YAML list var, render it explicitly (`| string`) — a bare single-variable template resolves to a native list, not text.
- Comment density is a feature: the task files carry the WHY comments the bash modules had. Keep lint clean (`.ansible-lint` skips exactly two style rules, with reasons in that file); prefer a `# noqa: rule` with justification over weakening a task.

## The GNOME extensions

`roles/desktop/window_snapping/files/rectangle@amamparo/` and `roles/desktop/no_overview/files/no-overview@amamparo/` are bundled, self-authored GNOME Shell extensions (ESM, GNOME 48–51), not vendored third-party ones — edit them directly here. The shared `gnome_extension.yml` mirrors them into `~/.local/share/gnome-shell/extensions/` with rsync; its rsync_opts are load-bearing for convergence (`--exclude=gschemas.compiled` — exists only in the installed copy; `--checksum` — tarball and git-checkout mtimes differ for identical content; `--omit-dir-times` — glib-compile-schemas rewrites schemas/ and bumps the dir mtime, which would re-report changed and re-compile forever). Schemas compile only when the sync changed (rectangle only). Enablement **merges additively** into `/org/gnome/shell/enabled-extensions`: the effective list is probed via `gsettings get` (NOT `dconf read` — vendor defaults like Fedora's background-logo live in gschema overrides, invisible in the user db) and the repo's `gnome_extensions_enabled` (site.yml) is unioned in — never overwritten, matching the old `gnome-extensions enable` append semantics; the "shell hasn't rescanned" race is gone because the write path IS the old fallback.

For rectangle: keybindings are declared in `schemas/*.gschema.xml` (the `as`-typed keys), consumed by name in `extension.js` (`KEYS`); `_unmaximize()` carries a GNOME ≤48 vs ≥49 API fallback. `metadata.json`'s `shell-version` gates which GNOME versions load an extension, and Wayland can't hot-reload GNOME Shell — extension changes take effect at logout/login.

## Gotchas encoded in the roles

- updates: sanctioned exception to the offline-converged-re-run rule, and it runs FIRST — later roles then resolve against fresh metadata. Its very first task writes `max_parallel_downloads=8` into `/etc/dnf/dnf.conf` (`community.general.ini_file`, become): the ONLY safe parallelism in this single-host play. libdnf5 downloads 3 packages at a time by default; every dnf transaction in the repo inherits the bump, so download phases overlap while the serial rpm transactions (one lock) never do — order untouched, check-mode honest, idempotent. Cross-TASK concurrency was rejected on evidence: async `poll: 0` is the only intra-host mechanism and it STARTS the real background job even under `--check` (verified: `started=True` in a dry run), which would execute installs during `./install.sh --check` — a hard violation of check-mode honesty. `forks` does nothing with one host; `pipelining` is ssh-only (local connection here). 8 is the Fedora-mirror sweet spot (past ~10, mirrors throttle). `update_cache: true` is what actually delivers the fresh-metadata promise: `state: latest` alone trusts any cache inside libdnf5's expiry window, and hours-stale metadata referencing mirror-pruned rpms 404'd podman-tui twice before this was understood. `state: latest` on `*` carries a `package-latest` noqa — latest is the concern here and in podman, nowhere else. fwupd exit codes (verified live): `get-updates` rc 0 = updates available, rc 2 = nothing to do — hence `failed_when: rc not in [0, 2]`; `update --assume-yes --no-reboot-check` applies without prompting, and staged firmware takes effect at reboot (the role says so). fwupd/flatpak tasks are guarded on the packages existing — Workstation ships both, minimal installs may not. **The out-of-dnf upgrades ride here too** (presence-guarded, so a machine that never ran those roles skips): Goose desktop (`'Goose' in ansible_facts.packages`, compare `'v' ~ version` with the `releases/latest` tag, re-run the shared `goose_desktop_install` include; `--check` prints the pending tag), ollama (probe the BINARY's version with `OLLAMA_HOST=127.0.0.1:1 ollama --version` — without that, `--version` reports the running daemon's version and only mentions the client's when they differ; compare against the `releases/latest` redirect's tag — the Location header, no api.github.com call, which was seen rate-limited here — and re-run the shared install include, which restarts the daemon inline because this role runs before the ollama role's handlers exist), litellm (`uv pip install --upgrade` in the venv followed by the shared cmp-gated `litellm_prisma_generate` include — a new litellm usually ships a new schema.prisma, whose migrations apply themselves at the restart but whose generated client we must rebuild — guarded on the UNIT file rather than the venv — a venv orphaned by a run that aborted before the unit was written would otherwise notify a restart of a unit systemd has never seen; uv prints `Installed N packages` on stderr only on change, `Checked N packages` otherwise — verified — and notifies this role's own `Restart litellm after upgrade` handler, named distinctly from the litellm role's because handler names resolve play-wide, last loaded wins), opencode (`opencode upgrade --method curl`, run with `~/.opencode/bin` prepended to PATH so a vendor script it re-executes never appends to ~/.zshrc; `changed_when` is `Upgrade complete` in stdout and `failed_when` catches `Upgrade failed`, which exits 0 — see the opencode bullet). Under `--check` the version probes run (read-only) but the upgrades themselves are skipped — `command` has no check-mode support and the ollama include's tempfile never sets `.path` — so a dry run prints a debug naming the pending ollama tag rather than a changed task.
- snapshots: snapper + libdnf5-plugin-actions + btrfs-assistant (all stock rpms) — pre/post btrfs snapshots of / around every dnf5 transaction, ordered right after updates so the rest of the very first run is already covered. `files/snapper.actions` is upstream dnf5's canonical DNF4-snapper-emulation example with two deliberate deltas, both explained in its header: `-c number` on both `snapper create` calls (number-cleanup only prunes snapshots carrying the "number" cleanup algorithm — upstream's example accumulates forever) and an inline python3 rpmdb WAL checkpoint before the post snapshot (rpm's sqlite runs WAL mode; a snapshot with unflushed frames makes rpm report packages that `snapper undochange` already reverted — SysGuides' F44 finding; python3 stdlib, no sqlite3 CLI dependency). Actions format: FIVE colon-separated fields, backslash-escaped spaces stay one argv element, `${...}` substitutes before unescaping, and there is NO shell unless the command is `sh -c` — the python line's quotes are python syntax, not shell. Plugin errors never abort the transaction (raise_error defaults to 0). Config creation is `create-config` guarded by `creates:` on /etc/snapper/configs/root; retention limits are SEEDED one-time on creation (`set-config` rewrites the file — converged management would fight snapper, the reaper.ini class), followed by a one-time `restorecon -RF /.snapshots` (the fresh subvolume is unlabeled). Timers ship disabled per Fedora's spec; enablement carries the battery fresh-`--check` gate. Scope: /home is a separate subvolume, so root snapshots never cover user files (same-disk undo only — offsite backup is deliberately out of scope here); /var IS inside root, so rollbacks rewind logs and system-side container state. Post-rollback trap documented in the role, not automated: dnf failing with "cannot copy: packages.toml" wants `mkdir -p /usr/lib/sysimage/libdnf5` + restorecon. Substring: `./install.sh snap` matches BOTH window-snapping and snapshots.
- hostname: sets the static hostname to `thinkpad` (LAN-reachable as `thinkpad.local`) via `ansible.builtin.hostname` with an explicit `use: systemd` — there is NO `FedoraHostname` class (verified: 35 distro subclasses, zero mention of Fedora), so autodetection rides one `is_systemd_managed()` canary whose fallback is base `Hostname` → `UnimplementedStrategy`, a HARD FAIL rather than a degrade; naming the strategy skips that path. `become: true` because `SetStaticHostname` is the polkit action `org.freedesktop.hostname1.set-static-hostname` (auth_admin_keep), which root short-circuits — no agent, no prompt under this repo's passwordless become. **The handler MUST be `state: restarted`, never `reloaded`:** avahi consults `gethostname()` exactly ONCE, in `avahi_server_new()`, and watches nothing afterwards (inotify covers only /etc/avahi and /etc/avahi/services; no `org.freedesktop.hostname1` subscription — `strings /usr/bin/avahi-daemon | grep hostname1` is empty; netlink is RTMGRP_LINK/IFADDR, interfaces not names), while `reload_config()` — reached by SIGHUP, `avahi-daemon -r`, and therefore the unit's own `ExecReload=` — reloads static services/hosts/resolv.conf/browse domains and NOT the host name, so a reload leaves the machine answering as the old name until reboot. The daemon's "-2" conflict rename is not a counterexample (it derives from the in-memory name in response to a packet). Equally, never write `/etc/hostname` with `copy`: it bypasses hostnamed, the running kernel name stays stale, and since avahi publishes whatever `gethostname()` returns the restart would then re-read the OLD name — the module sets permanent-then-transient (only `SystemdStrategy` overrides the base class's reverse order, "to avoid NetworkManager complaints"). **NEVER verify a rename with `getent`/`resolvectl` on this machine** — resolved answers the machine's own `<hostname>.local` locally without consulting avahi (mDNS is `-mDNS` in resolved on Fedora; avahi owns 5353): resolved says so itself, `resolvectl query fedora.local` closing with `Data from: synthetic` and returning every local address including ones avahi is not publishing, while a foreign `.local` name fails outright. Use `avahi-resolve -n <name>.local`, another host, or `busctl call org.freedesktop.Avahi / org.freedesktop.Avahi.Server GetHostName` (which also catches a silent `-2`). **avahi/nss-mdns are ASSUMED, never installed** (the updates-role fwupd/flatpak guard-on-presence precedent): Workstation ships both, and `nss-mdns`'s posttrans scriptlet runs `authselect enable-feature with-mdns4` — installing it would drag this repo into authselect, whose `with-fingerprint` the whole become design rests on. The guard is a PLAIN `'avahi' in ansible_facts.packages`, deliberately NOT the tailscale/battery `not ansible_check_mode or …` form: this role installs nothing, so an absent avahi is genuinely absent rather than simulated, and the tailscale form would evaluate true on a real run and hard-fail systemd_service on a unit that will never exist. Do NOT touch `/etc/hosts` (`files` precedes `myhostname` in the nsswitch hosts line, so a `127.0.0.1 thinkpad` entry would SHADOW the real LAN address; "fedora" is in no hosts file today and resolves fine both ways — the `sudo: unable to resolve host` folklore predates nss-myhostname), do NOT swap `mdns4_minimal` for dual-stack `mdns_minimal` (nss-mdns's README: IPv6-first apps time out), do NOT add a firewalld task (default AND active zone is FedoraWorkstation, which already permits 1025-65535/udp, so 5353 is open — the `mdns` service entry would fork a vendor zone file into a frozen copy for nothing), do NOT enable `publish-workstation` (pristine `config(noreplace)`; `_workstation._tcp` is the administrative "browse for all PCs on the LAN" advert in `avahi-daemon.conf(5)`'s own words, consumed by avahi-browse/avahi-discover and NOT by file managers, orthogonal to the `.local` A record, and avahi names it `<hostname> [<mac address>]` — a MAC broadcast on every roamed network). Today's "fedora" is `DEFAULT_HOSTNAME` in `/usr/lib/os-release` (fedora-release-identity-workstation), NOT DHCP and NOT `/etc/hostname` — which exists holding one newline as `%ghost %config(noreplace)` from systemd; `hostnamectl --json=short` reports HostnameSource `default`, StaticHostname null. A valid static name is also NetworkManager's own documented opt-out from touching the hostname, so no `hostname-mode=none`. The module's `--pretty --static` call really does set the pretty name (hostnamectl drops a redundant one only on its no-flags path), CREATING `/etc/machine-info` and moving GNOME's "Device Name" and the Bluetooth adapter alias — SEEDED once, never converged, since change detection reads only `--static`. Ordered slot 3, after snapshots (inside the first run's rollback coverage) and BEFORE tailscale, so the first-ever `tailscale up` registers `thinkpad`; never `tailscale set --hostname`, which permanently un-sticks the tailnet name from the OS hostname. **Renaming strands Chromium profile locks, which is why the role has a second half.** Chromium — and every Electron app, which embeds it — locks a profile with a symlink whose NAME encodes machine+pid (`~/.config/BraveSoftware/Brave-Browser/SingletonLock -> fedora-13834`). A stale lock naming THIS machine self-heals (ProcessSingleton checks the pid, finds it dead, breaks the lock — which is why an unclean browser exit is normally invisible), but a lock naming a DIFFERENT machine is never broken, since a profile in a shared/NFS home may genuinely be held by another host where breaking it would corrupt it. So the rename converts a self-healing lock into a permanent one: `process_singleton_posix.cc:365` "The profile appears to be in use by another Brave process (13834) on another computer (fedora)". **The failure is SILENT** — the very next line is `message_box_dialog.cc:200 Unable to show message box: <same text>`, because the dialog explaining the refusal is drawn BY the browser that just refused to start, so nothing reaches the screen and clicking the launcher looks like a no-op with no error anywhere a user would look. That silence is why this is automated rather than documented. Diagnosed live 2026-08-16: Brave ran as `fedora` at 02:03, a 02:22 reboot killed it before cleanup, this role renamed the host at 02:26, and the browser never started again. A pristine machine CANNOT hit it — hostname is slot 3 and brave slot 14, so Brave isn't installed when the rename happens and its first-ever lock already reads `thinkpad`; the reachable case is the FIRST `./install.sh` on an already-used machine. Four tasks sweep it, all `$HOME` so NO become (root's profiles aren't the wedged ones): `find` `SingletonLock` symlinks under `~/.config` (depth 3 reaches `BraveSoftware/Brave-Browser/`; a missing path warns rather than fails, so a fresh machine walks zero entries — and `~/.var/app` is deliberately out of scope: the one flatpak this repo installs, Podman Desktop, is an Electron app that lands after this rename in role order, and flatpak's PID namespace makes the host-side liveness check meaningless for a sandboxed lock — its recorded pid is the sandbox's — so the manual `rm ~/.var/app/<id>/config/*/Singleton*` is the fix there), `stat` with **`follow: false`** to read the target (find does NOT return link targets, and following would report the always-dangling relative target — nothing is ever named `fedora-13834` — as missing and lose the name), select those whose recorded host ≠ `hostname_set.name`, then remove all three `Singleton*` files (Cookie and Socket carry no hostname but belong to the same lock generation; removing the set is what was verified to un-wedge Brave) **only when `/proc/<pid>` is gone**. Compare against `hostname_set.name`, never the live `hostname`: the module returns its own `name` param unconditionally (verified in its source — `kw = dict(changed=changed, name=name, ...)` has no check-mode branch), so it reads `thinkpad` even on the `--check` run where the rename was only simulated, and the name stays one literal. Split on the LAST hyphen (hostnames may contain them: `old-host-name-4242`); RFC 1123 limits them to letters/digits/hyphen, so interpolating the name into the regex is safe. **The pid-alive case is deliberately SKIPPED, not fixed** — a browser running across the rename still owns its lock and cleans it up on exit, and the asymmetry is the point: guessing "stale" wrongly lets a second instance into a live profile and corrupts it, while guessing "held" wrongly costs one manual `rm` (the residual pid-reuse case gets a debug saying exactly that). Substring: `./install.sh host` matches BOTH hostname and ghostty; `hostname`/`name` hit only this role.
- steam: from RPM Fusion nonfree, so it MUST stay ordered after multimedia (which installs the release rpms); carries the same fresh-`--check` gate on `rpmfusion-nonfree-release`.
- battery: `tlp` declares `Conflicts: tuned` (`tuned-ppd` merely depends on tuned). The stock stack is removed *before* installing so its orphaned deps get swept — but the dnf5 *module*, unlike the CLI, only sweeps with `autoremove: true` (it wires `clean_requirements_on_remove` to that flag, default off); the removals here and in brave set it. Removals are guarded per exact rpm name because `tlp-pd` *provides* `power-profiles-daemon`. - fingerprint: two lines of systemd drop-in (`/etc/systemd/system/fprintd.service.d/stop-before-sleep.conf`) that stop fprintd before the machine sleeps. **fprintd is transient** — D-Bus activated by the greeter's pam_fprintd, exits ~30s after the last operation — and if a suspend lands inside that window the daemon rides through the sleep still holding an open USB handle. On resume that handle is a zombie: transfers return `endpoint stalled or request not supported`, the stale claim is never released (`Device was already claimed`), and pam_fprintd fails **with no grantor at all** (`op=PAM:authentication grantors=? res=failed`), so GDM/the lock screen silently drop the fingerprint option and offer only a password. Nothing surfaces an error anywhere a user would look, and the wedge clears itself when the instance idles out — which is exactly why it reads as random. Diagnosed live 2026-08-16 by interleaving `Started fprintd` / `Deactivated` against `PM: suspend entry`: every working cycle that day had fprintd stop BEFORE the suspend (02:23:42 stop → 02:24:36 suspend; 11:40:50 stop → 12:21:48 suspend), and both broken ones suspended 39s and 28s after a fingerprint prompt with no intervening stop. That interleave is the diagnostic — reproduce it before believing any other theory. **Why the handle zombies instead of reconnecting:** systemd's hwdb marks this sensor unsafe to keep across sleep (`systemd-hwdb query "usb:v06CBp00F9*"` → `ID_AUTOSUSPEND=1`, `ID_PERSIST=0`) and `60-autosuspend.rules` honours it at device add (confirm with `udevadm test /sys/bus/usb/devices/3-7`, which prints BOTH writes — a `head`-truncated grep will hide the persist one and fake a contradiction), but libfprint flips `power/persist` back to 1 at runtime: it is the only component that writes those paths (`strings /usr/lib64/libfprint-2.so.2` carries `/sys/bus/usb/devices/%d-%s/power/persist` and `Failed to disable USB persist by writing to %s`, and fprintd's unit grants `ReadWritePaths=/sys/devices` with the comment "Allow tuning USB parameters (wakeup and persist)"). With persist=1 a device that drops across suspend is silently reattached to the same fd rather than raising a clean disconnect. Do NOT chase that with a udev rule forcing `power/persist=0` — udev runs at add, libfprint's write comes later and wins, and stacking a second workaround is the no-overview trap. **NOT a TLP or power-saving bug, and that is the first wrong turn to avoid:** the sensor's `power/control=auto` comes from stock Fedora's `60-autosuspend.rules` acting on hwdb's `ID_AUTOSUSPEND=1`, so TLP setting it too is irrelevant and `USB_AUTOSUSPEND=0` would not change the value; runtime autosuspend also demonstrably works (`fprintd-verify` wakes the device `suspended` → `active` and reaches `Verify started!`). Hence its own role, NOT a battery add-on — the merge test fails on dependency direction. `Conflicts=sleep.target` is what performs the stop (starting a target stops units that conflict with it); `Before=sleep.target` is what makes the stop *finish* first, since systemd.unit(5) is explicit that Conflicts= carries no ordering of its own. Anchor on `sleep.target`, never `suspend.target`: systemd-suspend/-hibernate/-hybrid-sleep/-suspend-then-hibernate.service each declare `Requires=sleep.target` + `After=sleep.target`, so it is the one node all four modes share and it is reached before systemd-sleep acts. Stopping the daemon costs nothing here because `power/wakeup` on the sensor is `disabled` — there is no wake-on-finger to lose. The drop-in is deliberately UNGUARDED on fprintd being installed (contrast the hostname role's avahi guard, which exists only because systemd_service hard-fails on an absent unit): a drop-in dir for an unknown unit is ignored, and writing it unconditionally means the fix is live the first time fprintd is ever activated. The `daemon-reload` handler passes **no `name:`** — naming a unit makes systemd_service probe LoadState and hard-fail when absent (the battery power-profiles-daemon trap), while a bare `daemon_reload: true` touches no unit and stays honest under a fresh `--check`. Handler not converged task: daemon-reload can never report unchanged.
